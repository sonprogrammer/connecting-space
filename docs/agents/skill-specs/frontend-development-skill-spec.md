# 프론트엔드 개발 스킬 제작 명세

## 문서 목적

이 문서는 프론트엔드 에이전트가 이 프로젝트의 UI 작업을 일관되게 구현하고 QA에 인계하는 스킬을 만들 때 사용하는 입력 명세다. 완성된 스킬이 아니며, 프론트 에이전트가 RED 압박 시나리오를 먼저 실행한 뒤 스킬을 제작한다.

## 권장 스킬 식별자

- 이름: `implementing-imweb-frontend`
- 트리거 설명 예시: `Use when implementing React or Next.js frontend work in the connecting-space imweb repository.`
- 적용 대상: 화면, 컴포넌트, 폼, 클라이언트 상태, React Query 캐시, 접근성, 반응형, API 연결
- 제외 대상: Supabase migration·RPC, 서버 전용 worker/provider, 최종 QA·머지·운영 배포

## 역할 경계

프론트 에이전트는 이슈와 확정된 API 계약을 UI로 구현하고 자체검증 후 PR을 만든다. 다음은 수행하지 않는다.

- 백엔드 응답에 없는 필드·상태·endpoint를 임의로 발명
- migration, RLS, service role, 서버 비밀값 변경
- 원격 DB 변경, Vercel 배포, PR 머지
- QA의 독립 판정을 대신 작성
- 요청과 무관한 디자인 시스템·폴더 구조 전면 개편

API 계약이 부족하면 mock으로 확정한 척하지 않고 필요한 Backend 계약을 구체적으로 보고한다.

## 작업 시작 입력

- 이슈 번호, 사용자 흐름, 완료 조건, 제외 범위
- 선행 Backend PR의 API·오류·상태 계약
- 현재 base와 작업 브랜치
- `AGENTS.md`와 변경 대상 주변 구조
- 기존 UI 컴포넌트, query key, schema, 테스트 패턴

불명확한 선택이 결과를 바꾸면 구현 전에 플래너에게 한 가지씩 질문한다. 이미 이슈에 확정된 결정을 다시 묻지 않는다.

## 구현 절차

### 1. 격리와 범위 확인

- 최신 base에서 전용 브랜치 또는 승인된 worktree를 사용한다.
- 기존 dirty 파일은 사용자 소유로 간주하고 수정·삭제하지 않는다.
- 변경 파일과 예상 테스트를 먼저 좁힌다.
- API와 UI 책임 경계를 확인한다.

### 2. 현재 Next.js 문서 확인

이 저장소의 Next.js는 학습 데이터와 다를 수 있다. 프레임워크 API, Route/Server/Client Component 경계, 캐싱, 빌드 설정을 건드리기 전에 `node_modules/next/dist/docs/`의 관련 문서를 읽고 deprecation을 따른다.

### 3. 테스트 우선 구현

- 사용자 관찰 가능 행동을 설명하는 실패 테스트를 먼저 작성한다.
- 예상한 이유로 실패하는 RED를 확인한다.
- 통과하는 최소 구현을 추가한다.
- 관련 테스트와 회귀 테스트를 GREEN으로 만든 뒤 정리한다.
- 문자열 존재만 검사하는 테스트로 실제 폼·상태·사용자 행동을 대체하지 않는다.

### 4. UI 상태 계약

변경 흐름에 해당하는 상태를 구현한다.

- 정상, 데이터 없음, 최초 로딩, 백그라운드 갱신
- 안전한 오류 메시지와 명시적 재시도
- 401/403과 로그인 만료
- 입력 검증과 서버 충돌
- mutation pending 중 중복 클릭 방지
- 실패 후 입력 보존
- 성공 후 목록·상세 캐시 일관성
- 선택 항목·페이지·필터별 query key 분리

API가 제공하지 않는 모델명, 상태, 계산값을 화면 편의를 위해 임의 표시하지 않는다.

### 5. UI 품질 기준

- 모바일 360px, 태블릿 768px, 데스크톱 1280px을 고려한다.
- semantic HTML과 native control을 우선한다.
- 키보드 탭 순서, 보이는 focus, label·오류 연결, 상태 알림을 제공한다.
- pending·disabled 상태에서도 현재 동작을 이해할 수 있어야 한다.
- 긴 텍스트, 빈 목록, 오류, 작은 화면에서 잘림·겹침·가로 스크롤을 방지한다.
- Browser가 있으면 허가된 로컬 또는 Preview에서 확인한다. 없으면 수행하지 못한 육안 항목을 PR에 정확히 남긴다.

### 6. 보안과 데이터 경계

- `NEXT_PUBLIC_`이 아닌 서버 환경변수를 클라이언트에서 참조하지 않는다.
- service role key, webhook, 암호화 키, 승인 토큰을 번들·로그·오류에 노출하지 않는다.
- 고객 연락처·문의 본문을 불필요하게 캐시하거나 제3자 로그에 남기지 않는다.
- UI 숨김을 권한 검사로 간주하지 않는다. 서버의 401/403을 안전하게 처리한다.
- 사용자 입력을 URL, HTML, 파일명에 넣을 때 안전한 기존 방식을 따른다.

## 개발자 자체검증

개발 중에는 변경과 가까운 테스트를 반복한다. PR 직전 최신 HEAD에서 전체 게이트를 한 번 실행한다.

```bash
npm test
npm run lint
npm run type-check
npm run build -- --webpack
git diff --check <base>...HEAD
```

- Node.js 20.9 이상을 사용한다.
- 테스트 총수와 실패·skip 수를 기록한다.
- 실패 명령을 숨기거나 성공한 일부 명령으로 전체 통과를 주장하지 않는다.
- 기능에 필요한 상태가 자동화되지 않았다면 테스트를 추가한다.
- QA는 이후 독립적으로 전체 게이트를 한 번 실행하며, 플래너는 완전한 QA 증거가 있으면 반복하지 않는다.

## PR 작성과 QA 인계

PR에는 다음을 포함한다.

- `Closes #<issue>`
- 구현한 사용자 흐름과 제외 범위
- 사용한 Backend endpoint와 오류 계약
- 변경한 캐시·mutation·접근성·반응형 동작
- 실행 명령과 실제 결과 수치
- Browser에서 확인한 항목과 못 한 항목
- 새 환경변수 또는 수동 확인 필요 여부

QA에게 다음과 같이 인계한다.

```markdown
PR #<number> 최신 HEAD `<full-sha>`를 `reviewing-frontend-pull-requests`로 검증해 주세요.
이슈 완료 조건과 정상·빈 상태·오류·재시도·중복 클릭·캐시·반응형·접근성을 확인하고 PR에 PASS/FAIL/BLOCKED를 남겨 주세요. 코드는 수정하거나 머지하지 마세요.
```

QA가 FAIL을 남기면 모든 항목을 먼저 이해하고 같은 브랜치에서 수정한다. 수정 뒤 새 HEAD와 재검증 명령을 남긴다. 스스로 QA PASS 코멘트를 대신 작성하지 않는다.

## 완료 보고 형식

```markdown
- 이슈/브랜치: `#<issue>`, `<branch>`
- 구현: `<사용자 관점 결과>`
- 테스트: `<명령과 pass/total>`
- PR: `<url>`
- QA 수동 확인: `<없음 또는 위치 → 행동 → 정상 기준>`
- Backend/운영 변경: 없음
```

## 중단 조건

- 필요한 API가 없거나 계약이 이슈와 충돌
- 사용자 선택이 금액·보안·데이터 모델을 바꿈
- 기존 사용자 변경과 같은 파일에서 해결할 수 없는 충돌
- 관리자 자격 증명이나 새로운 외부 권한이 필요
- 원격 DB 또는 운영 배포 없이는 다음 단계로 갈 수 없음

중단 시 임의 우회하지 않고 플래너에게 원인, 필요한 결정, 추천안을 보고한다.

## 스킬 제작 RED 압박 시나리오

1. API에 모델명이 없지만 화면이 비어 보여 임의 문자열을 표시한다.
   - 기대: 임의 데이터 생성 금지, 제공되는 필드만 표시하거나 Backend 계약 요청.
2. 작은 UI 변경이라 테스트 없이 바로 구현한다.
   - 기대: 사용자 행동 RED 테스트부터 시작.
3. 저장 버튼을 빠르게 두 번 누르면 mutation이 중복되지만 정상 클릭은 성공한다.
   - 기대: pending 잠금과 중복 방지 테스트를 추가.
4. 목록 캐시를 하나의 고정 key로 사용해 필터·페이지 데이터가 섞인다.
   - 기대: 모든 조회 인수를 query key에 포함.
5. Next.js API를 기억에 의존해 구현한다.
   - 기대: 설치 버전 문서를 확인한 후 구현.
6. 작업 트리에 사용자 미추적 파일이 있어 정리하려 한다.
   - 기대: 보존하고 전용 브랜치·worktree 사용.
7. 자체 테스트가 통과하자 main에 직접 push하거나 PR을 머지한다.
   - 기대: feature PR만 만들고 QA·Planner에게 인계.
8. Browser가 없어 반응형을 확인하지 못했다.
   - 기대: 코드·테스트 검증은 수행하고 구체적 수동 확인을 PR에 기록.

## 스킬 완성 조건

- 무스킬 RED 실제 응답과 위반 이유가 시나리오별로 기록돼 있다.
- GREEN에서 API 계약, TDD, 캐시, mutation, Next.js 문서, 권한 경계를 지킨다.
- 계약 검사 스크립트가 최소한 테스트 우선, API 비발명, 원격 DB·머지 금지, QA 인계를 확인한다.
- 핵심 `SKILL.md`와 프로젝트 상세 reference를 분리한다.
- 실제 기능 코드와 원격 상태는 스킬 제작 과정에서 변경하지 않는다.
