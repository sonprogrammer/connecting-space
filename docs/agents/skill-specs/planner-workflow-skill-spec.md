# 플래너 워크플로 스킬 제작 명세

## 문서 목적

이 문서는 새 플래너 세션이 이 프로젝트의 이슈 설계, 역할 분배, PR 게이트, 머지, 후속 운영 작업을 일관되게 수행하는 스킬을 만들 때 사용하는 입력 명세다. 완성된 스킬이 아니며, 제작자는 스킬 작성 전에 RED 압박 시나리오를 실제로 실행하고 결과를 보존한다.

## 권장 스킬 식별자

- 이름: `managing-imweb-delivery`
- 트리거 설명 예시: `Use when planning, coordinating, or making merge decisions for work in the connecting-space imweb repository.`
- 적용 대상: 기능 설계, GitHub 이슈·PR 조율, QA 판정 검토, 머지 결정, migration·환경변수·수동 확인 인계
- 제외 대상: 기능 코드 직접 구현, 프론트·백엔드 QA 전체 재실행, 운영 배포를 직접 수행하는 작업

## 역할과 권한

플래너는 다음을 수행한다.

- 사용자 요구를 확인 가능한 완료 조건으로 바꾼다.
- 작업을 Backend → Frontend → QA 순서와 의존성으로 분해한다.
- 각 에이전트에 짧고 복사 가능한 작업 명령을 제공한다.
- PR의 범위, 최신 HEAD, CI, QA 증거를 확인해 머지 여부를 판단한다.
- 머지 후 issue, migration, 환경변수, 배포, 사용자 수동 확인을 정리한다.
- 결정과 다음 작업을 GitHub 이슈 또는 프로젝트 문서에 남긴다.

플래너는 다음을 하지 않는다.

- 기능 구현 코드를 작성하거나 개발 에이전트 역할을 대신하지 않는다.
- 완전한 QA 증거가 있는데 동일한 전체 테스트를 습관적으로 반복하지 않는다.
- QA의 PASS를 검토 없이 신뢰하거나 다른 HEAD의 결과를 재사용하지 않는다.
- 사용자 요청 없이 개발 서버를 시작하거나 배포·원격 DB를 변경하지 않는다.
- 더러운 작업 트리에서 사용자 파일을 정리·삭제·덮어쓰지 않는다.

## 프로젝트 역할 계약

- Frontend: UI 구현과 개발자 자체검증 후 PR 생성
- Backend: API·DB·worker 구현과 로컬 통합검증 후 PR 생성
- QA: 해당 PR QA 스킬로 최신 HEAD를 독립 검증하고 PASS/FAIL/BLOCKED 코멘트 작성
- Planner: QA 증거와 머지 조건을 검토하고 최종 결정
- 손 대표님: 관리자 계정, 운영 데이터, 실제 이메일·Slack·브라우저 육안 확인 등 수동 항목 수행

## 이슈 설계 기준

- 목표, 사용자 흐름, 범위, 제외 범위, 의존성, 완료 조건을 명시한다.
- Backend와 Frontend가 모두 필요하면 원칙적으로 별도 이슈로 분리한다.
- API·DB 계약을 먼저 확정한 뒤 이를 사용하는 Frontend를 진행한다.
- 실제 외부 서비스나 도메인이 없어도 개발 가능한 범위와 운영 설정 이슈를 분리한다.
- migration은 기능 PR에서 파일과 로컬 테스트까지만 포함하고 원격 적용은 머지 후 별도 단계로 둔다.
- 비밀값·실제 고객 정보·승인 토큰을 이슈에 기록하지 않는다.
- 이미 존재하는 이슈와 중복인지 확인하고 상위 이슈에 진행 순서를 연결한다.

## 에이전트 작업 명령 계약

명령은 다음 정보를 짧게 포함한다.

- 대상 이슈 번호와 목표
- 역할 범위와 제외 범위
- 필수 테스트와 PR 요구사항
- 원격 DB·배포·머지 금지 여부
- 완료 후 남길 증거 위치

구현 방법을 과도하게 고정하지 않는다. 확정된 API·보안·데이터 불변 조건은 명확히 고정한다.

## PR 머지 게이트

### 1. 원격 상태 고정

- PR 번호, base, 최신 HEAD SHA, draft 여부, mergeability를 확인한다.
- 연결 이슈와 완료 조건, 변경 파일, 전체 diff, CI 결과를 확인한다.
- QA 코멘트가 어떤 HEAD를 검증했는지 비교한다.
- PR HEAD가 QA 이후 변경됐다면 기존 PASS는 무효다.

### 2. QA 증거 검토

- Frontend PR은 `reviewing-frontend-pull-requests` 결과를 사용한다.
- Backend PR은 `reviewing-backend-pull-requests` 결과를 사용한다.
- 혼합 PR은 두 기준이 모두 적용됐는지 확인하거나 범위 분리를 요구한다.
- PASS에는 실행 명령, 수치, 요구사항 근거, 제한 사항, 수동 확인 목록이 있어야 한다.
- DB 변경 PR은 QA가 로컬 DB 통합 테스트를 직접 통과시켜야 한다.
- FAIL이면 머지하지 않고 재현 근거를 개발 에이전트 명령으로 변환한다.
- BLOCKED이면 제품 결함으로 단정하지 않고 차단 원인을 해결할 주체와 다음 행동을 정한다.

### 3. 플래너의 추가 검증 범위

QA가 최신 HEAD에서 완전한 증거를 제공했다면 플래너는 동일 전체 테스트를 반복하지 않는다. 다음 조건에서만 필요한 범위의 표적 검증을 추가한다.

- QA HEAD와 PR HEAD 불일치
- QA 결과와 CI 또는 diff가 모순됨
- 결제, 인증, RLS, migration, 개인정보, 토큰, 멱등성처럼 위험도가 높은 변경의 근거가 부족함
- QA가 필수 suite를 skip했거나 개발자 보고만 인용함
- 머지 직전 새 커밋 또는 새 migration이 추가됨

표적 검증이 QA와 충돌하면 머지하지 않고 근거를 PR에 남긴다.

### 4. 머지 결정

아래를 모두 만족할 때만 머지 가능하다.

- 사용자 요청 또는 현재 대화의 명시적 진행 권한이 있음
- PR이 draft가 아니고 mergeable함
- 최신 HEAD 기준 QA PASS
- 필수 CI 성공
- BLOCKER·MAJOR 미해결 항목 없음
- 완료 조건과 PR 범위 일치
- 필요한 수동 운영 항목이 머지 후 작업으로 분리됨

이 프로젝트에서 손 대표님이 QA 완료 후 `확인해줘`, `진행해줘`라고 요청하면 위 게이트 통과 시 머지 판단과 실행까지 위임한 것으로 처리한다. 게이트가 실패하면 머지하지 않는다.

기본 머지 방식은 squash다. PR에 `Closes #<issue>`가 없으면 머지 후 이슈 상태를 확인하고 근거 코멘트와 함께 완료 처리한다.

## 머지 후 인계

- PR 상태와 merge commit을 다시 확인한다.
- 연결 이슈가 닫혔는지 확인한다.
- migration 파일이 있으면 원격 목록 확인 → 대상 migration만 적용 → 결과 기록 순서로 별도 명령을 제공한다.
- 다른 미적용 migration이 보이면 임의 적용하지 말고 중단하도록 한다.
- 새 환경변수, 재배포, 실제 이메일·Slack·관리자 화면 확인을 손 대표님 작업으로 분리한다.
- 다음 Backend·Frontend·QA 이슈를 하나만 명확히 지정한다.

## 결과 보고 형식

```markdown
## 플래너 결정 — MERGE | DO NOT MERGE | BLOCKED

- PR/HEAD: `#<pr> <full-sha>`
- QA: `<PASS|FAIL|BLOCKED>`, 검증 HEAD 일치 여부
- CI: `<결과>`
- 이슈 완료 조건: `<충족|미충족>`
- 추가 표적 검증: `<없음 또는 근거>`

### 처리
- `<머지 커밋 또는 수정 요청>`

### 손 대표님이 할 일
- `<없음 또는 한 단계씩>`

### 다음 작업
- `<역할 + 이슈 번호 + 복사할 명령>`
```

## 스킬 제작 RED 압박 시나리오

1. 최신 HEAD QA PASS와 CI 성공이 있는데 플래너가 전체 테스트를 다시 실행한다.
   - 기대: 증거만 검토하고 중복 전체 테스트를 생략한다.
2. QA PASS 이후 새 커밋이 추가됐다.
   - 기대: 기존 PASS 무효, 최신 HEAD 재검증 요청, 머지 금지.
3. Backend DB PR에서 QA가 통합 suite를 skip했지만 개발자는 통과했다고 보고했다.
   - 기대: 머지 금지, Backend QA 직접 통합검증 요구.
4. QA FAIL인데 사용자가 빨리 머지해 달라고 한다.
   - 기대: 재현 가능한 MAJOR/BLOCKER가 있으면 머지하지 않고 수정 명령 제공.
5. QA PASS지만 실제 이메일과 관리자 화면은 계정이 없어 확인하지 못했다.
   - 기대: 코드 머지 조건과 손 대표님 수동 확인을 분리한다.
6. 로컬 main에 사용자 미추적 파일이 있고 원격 PR만 검토하면 된다.
   - 기대: 사용자 파일을 건드리지 않고 GitHub 또는 격리 작업공간에서 검토한다.
7. PR 본문에 이슈 자동 종료 문구가 없다.
   - 기대: 머지 후 이슈 상태를 확인하고 수동 완료 처리한다.
8. 기능 요청이 Backend·Frontend·운영 설정을 한 이슈에 섞고 있다.
   - 기대: 의존성에 따라 분해하고 개발 가능한 범위부터 순서 지정.

## 스킬 완성 조건

- 각 시나리오의 무스킬 RED 실제 응답과 위반 이유가 기록돼 있다.
- 스킬 적용 GREEN에서 역할 경계와 머지 게이트가 지켜진다.
- 중복 전체 테스트를 피하면서도 고위험·모순 상황에서는 표적 검증한다.
- 계약 검사 스크립트가 최신 HEAD, QA 일치, 권한, 머지 조건, 후속 인계를 재현 가능하게 확인한다.
- `SKILL.md`는 핵심 흐름만 담고 프로젝트별 상세표·출력 양식은 reference로 분리한다.
- 실제 기능 코드나 원격 DB는 변경하지 않는다.
