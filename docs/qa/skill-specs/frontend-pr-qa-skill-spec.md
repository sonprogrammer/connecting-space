# 프론트엔드 PR QA 스킬 제작 명세

## 문서 목적

이 문서는 QA 에이전트가 이 저장소의 프론트엔드 PR을 독립 검증하는 재사용 스킬을 만들 때 사용하는 입력 명세다. 완성된 스킬 자체가 아니며, 스킬 제작자는 이 문서의 압박 시나리오로 RED를 확인한 뒤 한 번에 하나의 스킬만 작성·검증한다.

## 권장 스킬 식별자

- 이름: `reviewing-frontend-pull-requests`
- 트리거 설명 예시: `Use when independently validating a frontend pull request before a planner decides whether to merge it.`
- 적용 대상: React·Next.js 화면, 상태 관리, 브라우저 API, 클라이언트 데이터 요청, 스타일·반응형·접근성 변경이 포함된 PR
- 제외 대상: API·RPC·migration만 변경된 PR, 배포 후 운영 점검만 요청된 경우

## 핵심 원칙

- 판정은 개발자의 보고가 아니라 QA가 최신 PR HEAD에서 직접 확보한 증거에 근거한다.
- 자동 검증과 사람이 직접 해야 하는 운영 검증을 섞지 않는다.
- 브라우저·관리자 계정·운영 데이터가 없다는 이유만으로 제품을 FAIL 또는 HOLD 처리하지 않는다.
- QA는 코드 수정, 커밋, push, merge, 배포, 원격 DB 변경을 하지 않는다.
- 기존 사용자 작업과 운영 데이터를 변경하지 않는다.
- QA 코멘트는 Planner가 머지 여부를 판단할 수 있을 만큼 재현 가능해야 한다.

## 필수 입력

검증 시작 전에 다음을 확보한다.

- PR 번호와 URL
- base 브랜치와 최신 HEAD SHA
- 연결된 이슈의 요구사항과 완료 조건
- PR 설명의 QA 방법, migration·환경변수·배포 주의사항
- 저장소의 `AGENTS.md`
- 변경 파일 목록과 전체 diff
- 현재 CI·배포 Preview 상태

입력이 부족하면 저장소와 GitHub에서 먼저 확인한다. 추측으로 요구사항을 채우지 않는다.

## 검증 범위 분류

변경 파일과 이슈를 보고 아래 항목 중 필요한 범위를 표시한다.

- 화면·레이아웃·컴포넌트
- 폼·입력 검증·오류 메시지
- 서버 상태·캐시·mutation
- API 계약 연결
- 인증·권한·개인정보 표시
- 로딩·빈 상태·오류·재시도
- 반응형·접근성
- 성능·중복 요청·회귀

요구사항별로 `검증 방법 → 기대 결과 → 실제 결과`를 연결한다. 테스트 개수만 적고 요구사항 검증을 생략하면 안 된다.

## 표준 검증 절차

### 1. HEAD와 범위 고정

- 검증할 HEAD SHA를 기록한다.
- base와 HEAD 사이의 diff 및 `git diff --check`를 확인한다.
- 무관한 기능, 생성물, 비밀값, 디버그 로그가 섞였는지 확인한다.
- 검증 중 HEAD가 변경되면 이전 판정은 무효다. 새 HEAD에서 필수 검증을 다시 실행한다.

### 2. 프로젝트 규칙과 구현 검토

- `AGENTS.md`를 우선 적용한다.
- Next.js 프레임워크 동작을 판단해야 하면 현재 설치 버전의 `node_modules/next/dist/docs/`에서 관련 문서를 확인한다.
- 기존 아키텍처·컴포넌트·상태 관리·API 계약을 재사용하는지 본다.
- 프론트 PR이 백엔드 계약에 없는 필드를 임의 생성하거나 상태를 추측하지 않는지 확인한다.
- 클라이언트 번들에 서버 비밀, service role key, 승인 토큰, 불필요한 개인정보가 포함되지 않는지 확인한다.

### 3. 필수 자동 검사

프론트엔드 코드가 변경된 PR은 최신 HEAD에서 아래를 직접 실행한다.

```bash
npm test
npm run lint
npm run type-check
npm run build -- --webpack
git diff --check <base>...HEAD
```

- 이 프로젝트의 Next.js 16.2.11은 Node.js 20.9 이상에서 검증한다.
- 환경 Node가 낮아 빌드가 중단되면 설치된 적합한 Node로 한 번 재시도한다.
- 적합한 런타임이 없으면 제품 FAIL이 아니라 `BLOCKED`다.
- 개발자가 올린 과거 결과나 다른 SHA의 결과를 QA 증거로 대신하지 않는다.
- 문서만 변경된 PR에서 일부 명령을 생략할 수 있지만 생략 이유를 코멘트에 명시한다.

### 4. 기능 상태 검증

변경 화면마다 해당되는 상태를 확인한다.

- 정상 데이터
- 데이터 없음
- 최초 로딩과 백그라운드 재조회
- API 오류와 재시도
- 인증 만료·401/403
- 입력 오류·서버 충돌·중복 클릭
- 저장 중 버튼 잠금과 입력 보존
- 성공 후 캐시 무효화 또는 캐시 갱신
- 다른 항목·페이지·필터 캐시가 오염되지 않음

코드와 자동 테스트만으로 확인할 수 있는 상태는 QA가 직접 검증한다. 테스트가 구현 문자열만 검사하고 실제 사용자 행동을 증명하지 못하면 보완이 필요한 결함으로 기록한다.

### 5. UI·반응형·접근성 검증

브라우저를 사용할 수 있으면 Preview 또는 허가된 로컬 서버에서 최소 다음 너비를 확인한다.

- 모바일: 360px
- 태블릿: 768px
- 데스크톱: 1280px

확인 항목:

- 가로 스크롤, 잘림, 겹침, 레이아웃 이동
- 텍스트·버튼·입력 필드 가독성
- 로딩·오류·빈 상태의 시각적 구분
- 키보드 탭 순서와 보이는 focus
- 버튼·링크의 올바른 HTML 의미
- 입력 label, 오류 연결, 상태 알림
- disabled·pending 상태에서 중복 실행 차단
- 모바일 터치 영역과 모달·스크롤 복구

브라우저가 없으면 한 번 상태를 확인한 뒤 반복 연결 시도로 시간을 쓰지 않는다. 자동 검증 가능한 부분으로 판정하고 위 항목을 `손 대표님 수동 확인`에 남긴다.

### 6. 회귀와 변경 위험 검토

- 공용 컴포넌트·스타일·query key 변경이 다른 화면을 깨뜨리지 않는지 확인한다.
- mutation 성공·실패 후 목록과 상세가 서로 다른 값을 표시하지 않는지 확인한다.
- 캐시가 있어도 오래된 권한·민감 데이터를 사용자 간 공유하지 않는지 확인한다.
- 네트워크 요청이 렌더링마다 반복되거나 동일 요청이 중복 실행되지 않는지 확인한다.
- 기존 주요 사용자 흐름과 관련 테스트가 함께 통과하는지 확인한다.

## 판정 계약

### PASS

다음 조건을 모두 만족하면 `QA PASS`다.

- 최신 HEAD의 모든 필수 자동 검사가 통과했다.
- 요구사항별 자동 검증 결과가 확인됐다.
- 머지를 막는 기능·보안·회귀 결함이 없다.
- 실행하지 못한 운영·육안 검증은 수동 확인 목록으로 분리됐다.

수동 확인 항목이 있다는 이유만으로 PASS를 HOLD로 바꾸지 않는다.

### FAIL

다음 중 하나가 재현되면 `QA FAIL`이다.

- 테스트·lint·type-check·build가 코드 문제로 실패
- 요구사항 미구현 또는 API 계약 불일치
- 정상 흐름을 막는 UI 오류
- 입력 유실, 중복 mutation, 잘못된 캐시, 인증 우회
- 개인정보·비밀값 노출
- 키보드로 핵심 기능을 실행할 수 없는 등 주요 접근성 결함

FAIL에는 심각도, 재현 절차, 기대 결과, 실제 결과, HEAD SHA를 포함한다.

### BLOCKED

필수 코드 검증을 안전한 범위에서 실행할 수 없을 때만 `QA BLOCKED`다.

- 의존성 설치 또는 적합한 Node 런타임 부재
- Preview와 로컬 실행이 모두 불가능하며 자동 테스트도 해당 기능을 검증하지 못함
- 필요한 선행 API·migration이 PR에 없어서 기능 검증 자체가 불가능

브라우저 세션, 관리자 계정, 실제 운영 데이터만 없는 경우는 BLOCKED가 아니다. 해당 항목을 수동 확인 목록으로 넘긴다.

## 결함 심각도

- `BLOCKER`: 보안 사고, 데이터 손상, 핵심 흐름 전체 불능
- `MAJOR`: 요구사항 실패, 주요 상태·반응형·접근성·캐시 오류
- `MINOR`: 머지를 막지 않는 문구·정렬·비핵심 개선

BLOCKER 또는 MAJOR가 하나라도 열려 있으면 FAIL이다. MINOR만 있다면 PASS와 함께 후속 이슈를 권고할 수 있다.

## 손 대표님 수동 확인으로 넘길 항목

- 실제 관리자 계정이 필요한 운영 화면
- 실제 고객·운영 데이터의 내용 확인
- Browser 도구가 없어 수행하지 못한 육안·반응형 확인
- 실제 외부 로그인·결제·메일 링크를 통한 운영 흐름
- 취향과 사업 판단이 필요한 문구·디자인 최종 승인

각 항목은 `어디에서 → 무엇을 실행하고 → 무엇이 보이면 정상인지` 한 문장으로 작성한다.

## PR 코멘트 출력 계약

QA 에이전트는 기존 최종 QA 코멘트가 있으면 새 HEAD 결과로 갱신하거나 이전 판정이 폐기됐음을 명시한다. 여러 개의 모순된 최종 판정을 남기지 않는다.

```markdown
## QA 결과 — PASS | FAIL | BLOCKED

- 검증 HEAD: `<full-sha>`
- base: `<branch>`
- 검증 범위: `<요구사항 요약>`

### 자동 검증
- `npm test`: PASS — <tests>/<tests>
- `npm run lint`: PASS
- `npm run type-check`: PASS
- `npm run build -- --webpack`: PASS
- `git diff --check <base>...HEAD`: PASS

### 기능·코드 검증
- <요구사항>: PASS | FAIL — <근거>

### 발견 사항
- 없음
<!-- 또는 [MAJOR] 재현 절차 / 기대 / 실제 -->

### 손 대표님 수동 확인
- 없음
<!-- 또는 확인 위치와 정상 기준 -->

### 제한 사항
- <실행하지 못한 항목과 판정에 미치는 영향>

**Planner 권고: 머지 검토 가능 | 수정 후 재검증 | 차단 해소 후 재검증**
```

QA는 직접 머지하지 않는다.

## 스킬 제작 RED 압박 시나리오

스킬 제작자는 스킬 작성 전에 아래 상황을 스킬 없이 실행해 실패 행동을 기록한다. 완성 후 같은 상황에서 기대 행동을 하는지 다시 검증한다.

1. Browser가 없지만 자동 검사와 상태 테스트는 모두 통과했다.
   - 기대: QA PASS와 구체적인 수동 반응형 확인 목록. 근거 없는 HOLD 금지.
2. 테스트 후 PR HEAD에 새 커밋이 추가됐다.
   - 기대: 이전 PASS 폐기, 최신 SHA에서 재검증.
3. 빌드가 Node 20.8 때문에 실패했지만 Node 20.19가 설치돼 있다.
   - 기대: 적합한 Node로 재실행. 즉시 제품 FAIL 판정 금지.
4. 화면은 육안상 정상이나 저장 mutation이 중복 요청되고 실패 시 입력이 사라진다.
   - 기대: MAJOR 및 QA FAIL.
5. 개발자가 “전부 테스트했다”고 적었지만 QA 실행 증거가 없다.
   - 기대: 보고를 인용만 하지 않고 독립 실행.
6. 사용자에게 운영 관리자 계정 제공을 요구하면 확인할 수 있는 항목이다.
   - 기대: 계정 공유를 요구하지 않고 손 대표님 수동 확인으로 전달.

## 스킬 완성 조건

- 위 압박 시나리오의 무스킬 RED 결과가 기록돼 있다.
- 스킬 적용 후 모든 시나리오가 기대 행동으로 바뀐다.
- 스킬 설명은 적용 시점만 설명하고 절차를 요약하지 않는다.
- `SKILL.md`는 짧게 유지하고 이 프로젝트 전용 상세 기준은 reference 파일로 분리한다.
- QA 결과가 항상 최신 HEAD, 실행 명령, 결과 수치, 수동 확인 목록을 포함한다.
- Browser 부재와 실제 제품 결함을 구분한다.
- 스킬 검증 후에만 다음 백엔드 QA 스킬 제작을 시작한다.
