# 관리자 제안서·계약서 편집 화면 설계

## 의도

관리자가 프로젝트의 제안서와 계약서 초안을 생성하고, 검토한 뒤 편집·저장·복사하며 이전 버전을 확인할 수 있게 한다. 장시간 문서 작업을 기존 프로젝트 편집 화면과 분리해 저장 상태와 검토 주의사항을 명확히 보여준다.

## 목표

- 프로젝트별 전용 문서 작업 URL에서 제안서와 계약서 초안을 관리한다.
- 생성, 편집, 저장, 복사, 이전 버전 조회 흐름을 제공한다.
- 초안이 검토 전 상태임을 분명히 표시하고 가격·일정·법률 항목은 확인 필요 상태로 보여준다.
- 인증, API 상태, 충돌 및 실패를 사용자가 이해하고 복구할 수 있도록 안내한다.
- 좁은 화면에서도 문서 편집과 주요 동작을 사용할 수 있게 한다.

## 범위 밖

- 실제 AI 제공자 호출 또는 생성 결과의 품질 변경
- 백엔드/API 계약 변경, 새 API 값 또는 모델명 추정
- 원격 DB migration, 배포, PR 머지
- 청구·계약 항목을 확정된 값으로 표시하거나 서버 소유 메타데이터 편집

## 제약과 기존 계약

- 기준 코드는 `origin/main`의 `3aab6a8d0bc0f2d752dd7516916014ba31cda2a6`이다.
- `docs/qa/issue-39-ai-documents.md` 및 병합된 GET/POST/PATCH `/api/admin/projects/{id}/documents` 계약을 따른다.
- 조회는 `cache: "no-store"`를 사용한다. 인증은 관리자 쿠키 기반이며 응답은 공통 `{data}`/`{error}` envelope다.
- GET은 현재 문서, 콘텐츠 없는 버전 목록, 페이지네이션 및 최근 최대 20개 작업을 제공한다. `version=N`은 이전 버전 콘텐츠를 읽기 전용으로 반환한다.
- POST는 `requestKey`로 멱등성을 보장한다. 진행 중인 같은 요청은 다시 생성하지 않으며, 실패 작업 재시도는 같은 키와 `retry: true`를 요구한다. 새 생성은 새 UUID 키를 사용한다.
- PATCH는 `expectedRevision`, `requestKey`, 편집 가능한 `title`, `summary`, `scopeItems`만 받는다. 같은 키/콘텐츠는 멱등이고 revision 충돌은 409다.
- `reviewOnly`, 서버 안내, 가격·일정 참조 및 `confirmed:false` 등 서버 소유 검토 정보는 표시만 하며 편집하거나 확정된 값처럼 취급하지 않는다.
- 오류 응답의 원문·제공자 세부 정보를 사용자에게 노출하지 않는다.
- 원격 migration 및 실제 AI 호출은 하지 않는다.

## 검토한 접근

1. **프로젝트 상세 화면 안에 편집기를 확장**: 이동이 적지만 이미 프로젝트/결제 편집 영역이 있어 장문 작성, 저장 상태, 버전 탐색이 과밀해진다.
2. **프로젝트별 전용 문서 작업 화면 (선택)**: 기존 프로젝트 상세에서 진입 링크를 제공하고 `/admin/projects/{id}/documents`에서 문서 탭, 편집기, 버전 이력을 제공한다. 기존 상세 화면을 크게 바꾸지 않으면서 문서 흐름을 집중시킬 수 있다.
3. **별도 관리자 전역 메뉴**: 진입은 쉽지만 프로젝트 문맥을 다시 선택해야 하고 현재 관리자 IA에 새로운 상위 메뉴를 추가한다.

전용 화면을 선택했다. 기존 관리자 메뉴와 프로젝트 상세의 문맥을 유지하면서 장시간 편집 공간을 확보한다.

## 화면 및 상호작용

- 프로젝트 상세의 문서 초안 링크에서 해당 프로젝트의 전용 URL로 이동한다. 기존 프로젝트 목록/상세와 AdminShell은 재사용한다.
- 상단에는 프로젝트 식별 정보, 프로젝트 상세로 돌아가기, 제안서/계약서 탭을 둔다.
- 본문은 현재 문서 편집기와 버전 이력으로 구성한다. 넓은 화면에서는 편집기 약 2/3, 이력 약 1/3의 2열, 작은 화면에서는 한 열로 쌓는다.
- 편집 가능한 필드는 제목, 요약, 범위 항목뿐이다. 검토 전 안내, 확인이 필요한 가격·일정·법률 항목, 출처 정보는 읽기 전용으로 별도 시각 구역에 둔다.
- 동작은 생성 또는 실패 작업 재시도, 저장, 복사로 제한한다. 저장하지 않은 수정이 있을 때 백그라운드 재조회가 입력을 덮지 않도록 한다.
- 복사는 현재 문서의 사람이 읽을 수 있는 내용과 검토 안내를 포함한다. 확인 전 가격·일정·법률 값을 확정된 약속처럼 복사하지 않는다.
- 버전 이력 선택은 해당 버전을 읽기 전용으로 연다. 현재 편집 내용을 자동 교체하거나 복원하지 않는다.

## 상태 및 오류 처리

- 초기 로딩: 편집기/이력 자리 표시와 접근 가능한 로딩 상태를 제공한다.
- 문서 없음: 빈 상태 안내와 새 초안 생성 동작을 제공한다.
- 생성 중(202 또는 진행 작업): GET으로 상태를 확인하고 진행 표시를 제공한다. 같은 요청을 반복 POST하지 않는다.
- 생성 실패: 안전한 요약과 명시적인 재시도 동작을 제공한다. 기존 실패 `requestKey`와 `retry:true`를 사용한다.
- 편집 중/저장 중: dirty draft를 보존하고 저장 진행/완료를 표시한다.
- revision 충돌(409): 입력 내용을 보존하고 최신 버전 재조회와 사용자의 명시적 재적용/재편집을 안내한다.
- 일반 조회/저장 오류: 민감한 서버 세부 내용을 숨기고 재시도 경로를 제공한다. 인증 오류는 기존 관리자 인증 흐름에 맡긴다.
- 이전 버전 없음: 빈 이력 상태를 제공한다.
- 가격·일정·법률 항목에는 API가 제공하는 확인 필요 표시를 유지한다.

## 반응형 및 접근성

- 360px 폭에서는 한 열, 탭 및 주요 버튼은 줄 바꿈/세로 배치하고 페이지 가로 스크롤을 만들지 않는다. 이력은 편집기 아래에 둔다.
- 태블릿(약 768px)은 한 열을 기본으로 하되 충분한 폭에서 이력 밀도를 높인다.
- 데스크톱(약 1280px 이상)은 편집기/이력 2열을 사용한다.
- 탭, 입력, 저장 상태, 오류 및 검토 정보는 키보드 접근과 의미 있는 레이블/상태 텍스트를 갖는다. 색상만으로 상태를 구분하지 않는다.

## 데이터와 캐시

- 기존 프로젝트 상세 조회/도우미를 재사용한다. 문서 조회 key는 프로젝트 ID, 문서 종류, 페이지 또는 선택 버전을 구분한다.
- 모든 문서 GET은 API 계약대로 `cache: "no-store"`를 지정한다.
- 생성·저장 후 관련 문서 query를 갱신한다. dirty editor는 refetch 결과보다 사용자 입력을 우선 보존한다.
- 진행 작업 확인은 GET만 사용한다. 폴링 간격은 구현 단계에서 서버 부하를 고려해 적당한 값으로 선택한다. API 계약상 고정 간격은 없다.
- 버전 목록은 최대 20개 작업만 제공될 수 있어 오래된 모델/provider 정보를 사용할 수 없을 수 있다. 없는 정보는 추정하지 않고 출처/시각만 표시한다.

## 미확정 사항과 구현자 판단

- 진행 상태 polling의 고정 주기는 API 계약에 없다. 구현자는 적절한 간격과 종료 조건을 정하되 새 생성 요청을 반복하지 않는다.
- 최대 20개 작업 밖의 오래된 버전에는 모델 정보가 없을 수 있다. API가 돌려준 값만 보여준다.
- 문서 전용 화면 URL과 화면 구조는 선택한 설계로 고정한다. API에 없는 기능이나 값은 추가하지 않는다.

## 완료 기준

- 프로젝트 상세에서 제안서·계약서 전용 화면으로 이동할 수 있다.
- 두 문서 유형의 생성, 편집, 저장, 복사 및 이전 버전 읽기 전용 조회가 API 계약과 일치한다.
- 생성 중 중복 호출, refetch에 의한 입력 덮어쓰기, revision 충돌의 데이터 손실이 없다.
- 로딩/빈 상태/오류/검토 필요 정보가 접근 가능하고 반응형 레이아웃이 동작한다.
- 단위/통합 테스트 및 프로젝트 검증 명령의 실제 결과가 PR에 기록된다.
