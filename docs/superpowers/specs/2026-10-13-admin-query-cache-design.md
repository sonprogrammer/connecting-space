# 관리자 조회 캐시 설계

## 목표

관리자 메뉴를 이동해도 유효한 조회 데이터를 재사용하고, 업무함의 추가 페이지를 같은 스냅샷으로 중복·누락 없이 연결한다. 기존 API 계약을 따르며 관리자 요청의 `cache: "no-store"`를 유지한다.

## 현황과 API 계약

- 공용 관리자 `QueryClient`에는 이미 `staleTime: 30_000`(30초), `gcTime: 300_000`(5분)이 설정되어 있다.
- 고객·프로젝트·프로젝트 결제 조회는 이미 React Query를 사용한다. 조회 인수를 key에 포함하고 fetcher는 `cache: "no-store"`를 사용한다.
- 관리자 오늘 할 일 화면은 `/api/admin/work-items`를 직접 fetch하고 로컬 상태로 결과와 추가 페이지를 관리한다.
- `/api/admin/work-items`는 `group`, `sort`, `page`, `pageSize`, `asOf`를 받고 `counts`, `pagination.total`, `pagination.hasNextPage`, `asOf`, `items`를 반환한다. 기본 정렬은 전체 그룹에서 `waiting`, 업무별 그룹에서 `latest`다.
- 이 API 응답의 우선순위와 정렬 순서는 서버가 결정한다. 프론트엔드는 페이지 데이터를 재정렬하지 않는다.
- 별도의 `/api/admin/inquiries` 레거시 목록은 최대 100건 배열이며, 이 작업에서 그 endpoint 계약은 변경하지 않는다.
- 대시보드 문의 목록·상세, 관리자 포트폴리오 목록, 서비스·FAQ, 문의 답변 초안 조회는 컴포넌트에서 직접 fetch한다. 메뉴 이동 때 조회 캐시를 재사용하지 못한다.

## 선택한 접근 방식

오늘 할 일 업무함에는 `useInfiniteQuery`를 적용한다. query key는 `group`, `sort`, `pageSize`를 포함한다. 첫 페이지는 page 1 및 `asOf` 없는 초기 pageParam으로 조회한다. 다음 페이지는 마지막 응답의 `pagination.hasNextPage`가 참일 때만 요청하며, page를 1 증가시키고 첫 페이지 응답의 `asOf`를 그대로 전달한다. 그룹 또는 정렬 변경은 별도 key의 첫 페이지 조회로 시작한다.

업무함에서 성공한 변경 후에는 업무함 query를 새 첫 페이지와 새 `asOf`로 재조회하도록 초기화/무효화한다. 페이지 1을 새로 조회하지 않고 과거 스냅샷 pageParam을 이어 쓰는 상태가 남지 않게 한다. 변경은 페이지네이션 중인 목록만 수정하며 서버 우선순위에 따른 레코드 순서를 클라이언트가 바꾸지 않는다.

그 외 컴포넌트 로컬 관리자 GET 데이터(레거시 문의 목록·상세, 포트폴리오 목록, 서비스·FAQ, 답변 초안)는 공용 QueryClient의 `useQuery`로 옮긴다. 고객·프로젝트·결제의 기존 query 구현은 유지한다. query 함수는 `cache: "no-store"`를 사용하며 현재의 인증 처리, 오류 문구, 수동 새로고침/재시도 동작을 보존한다.

대안: 대시보드 업무함에만 React Query를 적용한다. 핵심 페이지 연결은 해결하지만 다른 관리 메뉴에 같은 캐시 손실이 남아 선택하지 않는다.

대안: 공용 key 하나로 관리자 데이터를 캐시한다. 메뉴·필터·정렬 응답이 충돌할 수 있어 선택하지 않는다.

## Query 식별과 탐색 동작

- 업무함 query key는 그룹·정렬·페이지 크기를 포함한다. 페이지 번호와 `asOf`는 key가 아닌 infinite query의 pageParam으로 관리한다.
- 다음 페이지 pageParam은 이전 페이지 번호 + 1이며 `asOf`는 첫 페이지 응답의 값을 고정해 사용한다. 정렬/그룹 변경 시 기존 pageParam은 이어 쓰지 않는다.
- 업무함 A→B→A를 30초 안에 이동하면 A의 key에 해당하는 성공 캐시를 재사용하고 불필요한 HTTP 요청을 하지 않는다.
- 레거시 문의 목록은 고정 목록 key를 사용한다. 문의 상세와 답변 초안은 문의 ID를 각각 별도 key에 포함한다.
- 포트폴리오, 서비스 제공 항목, FAQ는 각각 독립된 key를 사용한다. 기존 고객·프로젝트·결제 key factory는 유지한다.
- 메뉴 이동 시 공용 QueryClient를 초기화하지 않는다. 30초 이후 동작과 미사용 5분 GC는 기존 공용 설정에 맡긴다.
- 성공 캐시가 있는 상태에서 백그라운드 갱신이 실패하면 캐시 데이터와 기존 오류/재시도 안내를 함께 유지한다. 401/403의 현재 인증 처리도 보존한다.

## 변경 후 캐시 일관성

성공한 mutation만 관련 query 영역을 무효화한다. 실패한 mutation은 캐시를 무효화하지 않는다.

- 문의 상태 변경·답변 저장·프로젝트 전환은 업무함 목록과 관련 문의 목록/상세/답변 초안 조회를 무효화한다. 프로젝트 전환은 고객·프로젝트 목록도 무효화한다.
- 견적 작성·발송·재시도·승인 또는 취소 등 업무 항목 상태를 바꾸는 견적 동작은 업무함 목록을 무효화한다.
- 결제·영수증 변경은 업무함 목록과 영향을 받는 결제 상세를 무효화한다.
- 고객·프로젝트 저장은 해당 목록을 무효화하고 저장된 상세를 반환 엔티티로 갱신하는 기존 동작을 유지한다.
- 포트폴리오·서비스 제공 항목·FAQ 변경은 대응하는 목록 key 영역을 무효화한다.
- 업무함 캐시 갱신은 새 스냅샷의 첫 페이지부터 시작하며, 이전 페이지들을 섞지 않는다.

## 건수와 페이지 연결

- 업무함 전체 그룹은 응답의 `pagination.total`을 전체 건수로 표시한다. 그룹 필터 시에는 해당 응답의 `pagination.total`을 현재 그룹 전체 건수로 사용한다. 그룹의 `counts`를 pagination total 대신 표시하지 않는다.
- “불러온 건수”는 infinite query의 모든 페이지에서 실제로 받아온 `items.length` 합계로 별도 표시한다.
- 추가 페이지는 서버가 반환한 순서를 보존해 이어 붙인다. 첫 페이지와 같은 `asOf` 및 다음 연속 page를 사용한다. 25건을 넘는 결과에서 예상한 모든 항목이 한 번씩만 표시되는지 테스트한다.
- 고객·프로젝트 화면은 기존 페이지 번호 기반 이동을 유지하고 각 페이지를 별도 query로 캐시한다. API의 전체 `total`과 현재 페이지의 로드 건수를 구분해 표시한다.
- 레거시 문의 배열에는 계약에 없는 전체 건수를 표시하지 않는다.

## 테스트 및 완료 기준

- 업무함 query key 테스트는 group·sort·pageSize별 분리와 같은 값 재사용을 확인한다.
- A→B→A QueryClient 테스트는 A의 fetch가 30초 내 한 번만 실행되는지 확인한다.
- 25건 초과 업무함 테스트는 다음 페이지 요청의 `asOf` 동일성, page 연속 증가, `hasNextPage` 종료, 서버 순서 보존, 중복/누락 없는 ID 집합, 필터 그룹의 `pagination.total`, 별도 loaded count를 검증한다.
- fetcher 테스트는 관리자 GET에 `cache: "no-store"`가 남아 있고 기존 응답/오류 계약을 처리하는지 확인한다.
- mutation 테스트는 성공 시 관련 목록이 초기 페이지/새 스냅샷으로 갱신되고 실패 시 무효화하지 않는지 확인한다.
- 로딩, 빈 결과, 오류/재시도, 인증 실패, 그룹/정렬, 기존 검색/필터/페이지 이동, 변경 작업 회귀를 테스트한다.
- PR 전 `npm test`, `npm run lint`, `npm run type-check`, `npm run build -- --webpack`, `git diff --check`를 실행하고 실제 결과와 수동 브라우저 확인 여부를 기록한다.
- 원격 DB, 배포, 머지는 범위에서 제외한다.

## 명시적 제외 범위

- API endpoint/계약 변경.
- 백엔드, 데이터베이스, migration, 배포, 머지 작업.
- 관리자 디자인이나 라우팅 개편.
